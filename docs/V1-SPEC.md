# V1 Spec — Local AI on your PC

This is what Claude Code builds. Everything not listed here is **Later**.

## Goals v1 must deliver
1. Local open-weight models with skills and a harness, usable from your devices.
2. Two-way handoff: Claude → local (`ask_local_model` MCP tool) and local → cloud (`escalate_to_cloud` via the gateway).
3. A skill guide per chosen open-weight model.
4. Cost-aware, secure, and mostly automated.

## Decisions already made (don't re-ask)
- Use hardware you already own first; keep cloud spend small and capped.
- v1 devices: **Your PC** (home node, NVIDIA GPU) + **Your Mac** (edge device that can also run its own local models), plus a phone/tablet via browser.
- Cloud API keys to start: **Anthropic, OpenRouter** (OpenRouter for big open-weight models, synthetic or redacted data only).
- Stack: Ollama → **LiteLLM** gateway → clients (**Open WebUI** for phone/tablet/browser, **goose** on laptop, **Claude Code** for coding with Claude, **OpenCode** for coding with the routed models). Every client uses the gateway's `auto` model by default. VS Code optional.
- Electricity: batch jobs auto-scheduled out of your utility's peak window with a notice; ask only when a big job is started interactively during peak.
- **Mac local models:** the Mac may run Ollama for offline/travel use, bigger models and coding, under the same security rules (`docs/setup/MAC.md`). Your PC stays the only home for the gateway, MCP server, evals and provider keys.

## Handoff Packet (shared contract, both directions)
```json
{
  "packet_version": "1.0",
  "task_id": "uuid",
  "from_agent": "local:<model> | claude",
  "to_agent": "claude | local:<model>",
  "task_type": "summarize | classify | extract | redact | reason | draft | review",
  "goal": "One sentence describing the outcome wanted",
  "input": "The content to work on",
  "context": "Only the background the receiver needs",
  "constraints": ["e.g. max 120 words", "no PHI in output"],
  "output_schema": { "type": "object", "properties": {} },
  "attempted": "What the sender already tried and why it failed (escalations only)",
  "confidence_required": "low | medium | high"
}
```
Response adds: `status` (done / partial / failed), `output`, `confidence` (0–1), `notes`.
Routing fields (complexity score, selected model, estimated cost, etc.) are added in v1-4 only as far as the simple tier table needs; the full routing block is Later.

## Routing
**Automatic by default:** every client uses `auto`; you ask or give a task and the router picks the model in the background. Each conversation's first message is classified into a task type (plain-language criteria per tier); typed requests (MCP calls, Handoff Packets) carry theirs. The tier comes from a table generated from eval results into `router/`: per task type, the cheapest eligible tier that meets the routine bar in `compare` (every rule check passes, judge ≥ 4). Role aliases: `auto-plan` (planning, a strong tier), `auto-explore` (search and reading, the cheapest tier). The router switches only at a new user message, never across the agent's tool calls within a turn. The **dropdown** lists the tiers for a manual pick: it skips the table, the cost rule and escalation for that conversation, never the safety rules, and is logged as `manual`. Coding runs locally only on the Mac; on the PC it starts at Haiku. Cost per completed task and turns per task are tracked, because a cheap model that needs more turns can cost more.

**Knowing when a tier isn't enough:** every answer shows its model, tier, cost and local/cloud, with a "try a stronger model" action. Four layers judge each tier per task type: evals (the routine bar on held-out items, including hard ones, and not clearly behind Opus), run-time signals, your own signals (thumbs down, stronger-model clicks, regenerations, re-asked requests, dropdown overrides), and audits (Opus grades a random 5–10% of answers from lower tiers; a daily canary set per task type). With at least 30 answers in 14 days, an audit average below 4 or negative signals above 10% moves that task type up one tier automatically; it moves back down only after fresh evals and 14 days of audits clear the bar. Every move is logged and versioned.

**Escalation:** checkable task types (redact, extract, classify, JSON output) cascade one tier when the run-time checks fail: valid JSON against the packet's `output_schema`, required fields present, PII patterns for redaction (the generic checks in `evals/checks.py`). They catch format and leak failures, not subtle wrong answers. Judgment task types are routed up front, with no cascade. Interactive requests escalate at most once; batch work may cascade through every tier. The packet's `confidence` is logged but drives nothing until evals show it separates right from wrong on that task type. Escalation rate per task type is a tracked metric.

**Fallback complexity score** (computed in code, 1–5), only for task types with no eval data yet: start at 1; +1 each: reason/review/code task · multi-step · ambiguous or judgment-heavy · high stakes (customer-facing, compliance) · local attempt already failed validation. **High-stakes flags are set in code and can't be lowered.** A model may propose a score; it is logged only.

## Cloud tiers and OpenRouter
| Tier | Where | Used when |
|---|---|---|
| 1 | Local (the machine's primary/fast model) | Default where it meets the routine bar for the task type |
| 2 | Claude Haiku 5.5 (Anthropic API) | Task types local doesn't handle, or a local answer failed the run-time checks |
| 3 | Big open-weight model via OpenRouter | Only if the request is synthetic or locally redacted **and** the model's measured cost per task for that task type (OpenRouter fee included) is lower than Opus's; then for task types where it meets the bar, or after Haiku failed the run-time checks. Otherwise skipped |
| 4 | Claude Opus 5.5 (Anthropic API) | Judgment-heavy or high-stakes task types, or the tier below failed. Raise effort before switching model where that's cheaper |

Model names per tier live in `router/` config, never in code. Sonnet 5.5 is added between tiers only if evals show a gap. The cost comparison for tier 3 is re-checked at each price check; the v1-4 business case tunes the rest.

**OpenRouter rules** (enforced in the gateway config, not just written down):
- Synthetic or redacted data only, **except code from your own repos** (public and private), which is allowed under its repo's gateway key, the secret scan and zero data retention. Otherwise only Handoff Packets marked synthetic, or that passed local redaction, may use an OpenRouter route. As a routing tier it is also used only where it's cheaper per task than Opus (§Cloud tiers).
- Every request: providers that don't collect data (`provider.data_collection: "deny"`) and zero data retention only; no `:free` model variants (they can log prompts); `require_parameters: true` so only providers that support the request's features (tools, JSON) serve it. Zero data retention is also enforced at the account (ZDR-only, which also excludes "safety retention" endpoints) and on the key with a guardrail, so a client that forgets the request flags is still covered.
- Eval runs pin the provider (`provider.order`, `allow_fallbacks: false`, and a `quantizations` filter) and record the provider that served each result, like the Ollama version and model digest for local runs, because one model name can be served at different quantizations.
- Spend: prepaid credit with a per-key credit limit at OpenRouter, plus the gateway's per-call/daily/monthly caps.
- OpenRouter's settings and fees change: check its current docs before configuring (v1-2) and at each gateway upgrade.

## Model-origin rule
Wherever a Chinese model is a candidate (local or OpenRouter), the closest American open-weight model that fits the same machine is tested next to it on the same eval. Decided **per task type** (redaction, summary, extraction, ...):
1. **Quality winner:** more items passing all rule checks wins; equal rule results go to the higher judge average. A real win needs **2+ items or 0.3 judge points** (2 since 2026-11-20: one item is noise on 10-item sets, so results are indicative until the sets grow); anything smaller is a tie, and **ties go to the American model**. An item stuck at the token cap counts as a fail.
2. **Cost:** $/task. Cloud: token price incl. OpenRouter's fee. Local: seconds per item × the machine's typical draw under load (watts, in `router/` config) × the utility's time-of-use rate at run time (your PC's clock). Electricity is a fraction of a cent per item, so between two local models on one machine this is a speed comparison. Measured watts replace the assumed ones with the v1-4 benchmark report.
3. **Who stays:**
   - Chinese model wins: keep it, plus the closest American model as fallback.
   - American model wins or ties: keep only the American model, unless the Chinese one is **at least 25% cheaper** and meets the **routine bar** on that task type (every item passes all rule checks, judge ≥ 4).
   - Either way, a model that meets the routine bar and is ≥25% cheaper than the quality winner takes that task type's **routine work**; the winner takes the rest. A model kept for nothing is retired per the version-cleanup rule (ask before deleting).
4. **Re-check** at each new model version, each price check, and each official eval run.

`uv run evals/run.py compare --a RUN[:MODEL] --b RUN[:MODEL]` applies steps 1 and 3 per task type (makers and countries come from `router/models.json`); it compares only items both runs answered in the same version, and uses seconds per item for cost until watts are measured.

**Pricing (all providers the same, OpenRouter included):** prices come from config (`router/`) and LiteLLM's price map, never hard-coded. They're checked when the gateway is set up and at every LiteLLM upgrade, and the cost of a new kind of run is measured on a small batch first. OpenRouter adds its own fee on credit purchases; include it in $/task. Routine price checks run `router/prices.py` only. **At each version release (v1-x) and at gateway setup, also re-check the one-key alternatives** (search first; fees change): marketplaces (OpenRouter, Requesty, Vercel AI Gateway, Hugging Face Inference Providers, Abacus.AI RouteLLM), bring-your-own-key gateways (LiteLLM, Portkey, Cloudflare AI Gateway), open-model hosts (Together, Fireworks, DeepInfra, Groq) and cloud platforms (AWS Bedrock, Google Vertex, Azure AI Foundry). Compare markup and fees, privacy controls (no data collection, zero retention) and tool-call support; add a dated entry to `logs/price-checks.md`. Switching providers or adding a key is a human decision, not part of the check. Run `router/prices.py` (v1-2) for the per-model numbers. A scheduled price refresh is Later and covers every provider.

## Languages
Python for logic (typed, `ruff`-clean, pytest-tested, run with `uv`). Shell/PowerShell only as thin wrappers around OS tools (`sandbox-exec`, `docker`, `codesign`, service start-up). SQLite for anything queried later. One optional TypeScript piece: the v1-4 demo UI.

## Binding security rules (from the plan review)
- Keys: Windows Credential Manager → keyring → LiteLLM process only. Never env vars, `.env`, files, logs. gitleaks pre-commit.
- Model servers on localhost; gateway is the only entry; each client its own virtual key + budget.
- Tailscale ACL + MFA + device approval **before** exposing anything. Open WebUI admin created immediately; sign-ups off.
- Synthetic data only; work repos/data refused by every lane. OpenRouter routes get synthetic or redacted packets only, or code from your own repos under a per-repo key and a secret scan, always with no data collection and zero retention (§Cloud tiers and OpenRouter).
- Every model download needs your approval; files verified against their sha256; first load/eval in an isolated, no-network environment with models read-only (**PC:** `--network none` container; **Mac:** macOS sandbox, since Docker there has no GPU or MLX). GGUF/safetensors only (MLX models are safetensors).
- Pin dependencies: LiteLLM by image digest, Python by `uv.lock`, actions by commit SHA; checks run on every push. Review any MCP server, Open WebUI function, or plugin before installing.
- No AI path to PDU outlets, UniFi admin, or Home Assistant admin.
- Backups: Open WebUI data, evals and skills to the HDD with a restore test (v1-4); encrypted offsite is Later.
